"status=3이 무슨 뜻이에요?" 데이터 정의, 아직 한 사람 머릿속에만 있나요?

새로 온 분석 담당자가 주문 테이블을 열어 봅니다. status 컬럼에는 1부터 7까지 숫자가 들어 있고, amt와 amt2가 나란히 있으며, del_yn이 Y인 행도 섞여 있습니다. 결국 메신저로 묻습니다. "status 3이 무슨 뜻이에요? amt2는 뭔가요?" 답을 아는 사람은 시스템을 처음 만든 개발자 한 명뿐이고, 그분은 오늘 휴가입니다. 데이터가 없는 것이 아니라, 데이터의 뜻이 기록되어 있지 않은 것이 문제입니다. 이 글은 컬럼과 코드값의 의미를 데이터 사전으로 정리하고, 시스템이 바뀌어도 사전이 낡지 않게 자동으로 점검하는 방법을 정리합니다.

컬럼 이름만 보고는 알 수 없는 것들

대부분의 업무 시스템은 개발 당시의 편의에 맞춰 컬럼 이름을 짓고, 의미는 화면 코드나 담당자의 기억 속에 남겨 둡니다. 데이터를 직접 꺼내 쓰기 시작하면 다음 질문이 반복됩니다.

데이터 사전과 지표 정의서는 다릅니다

"매출은 어떻게 계산하는가"를 정리한 지표 정의서를 이미 갖춘 회사도 많습니다. 데이터 사전은 그보다 한 단계 아래, 계산에 쓰이는 재료 하나하나의 뜻을 정리합니다.

구분지표 정의서데이터 사전
다루는 대상매출, 활성 고객, 재구매율 같은 지표테이블, 컬럼, 코드값
답하는 질문"이 숫자는 어떻게 계산하는가""이 칸에 들어 있는 값은 무엇을 뜻하는가"
주로 보는 사람경영진, 현업, 보고서 작성자데이터 담당자, 개발자, 분석가, 자동화 설계자
틀렸을 때팀마다 숫자가 다름지표 정의가 맞아도 재료를 잘못 골라 숫자가 틀림

둘은 서로를 보완합니다. 지표 정의서에 "출고 완료 주문만 포함"이라고 써 두었다면, 데이터 사전에는 "출고 완료 = status 4"라는 연결 고리가 있어야 실제 계산이 정의와 일치합니다.

처음부터 전부 쓰지 말고, 자주 쓰는 데이터부터

테이블이 수백 개인 시스템의 모든 컬럼을 한 번에 정리하려고 하면 대개 중간에 멈춥니다. 실제로 많이 쓰이는 범위부터 시작하는 편이 현실적입니다.

  1. 범위 정하기: 보고서·대시보드·정기 추출에 실제로 쓰이는 테이블과 컬럼을 목록으로 뽑습니다. 자주 쓰는 쿼리에 등장하는 컬럼이 출발점입니다.
  2. 구조 자동 수집: 테이블명, 컬럼명, 데이터 형식은 데이터베이스의 메타데이터에서 자동으로 가져와 빈 사전 틀을 만듭니다. 사람은 의미만 채우면 됩니다.
  3. 코드값 실제 분포 확인: 코드 컬럼마다 실제로 들어 있는 값과 건수를 뽑아 봅니다. 문서에 없는 값, 오래전에 쓰다 멈춘 값이 이 단계에서 드러납니다.
  4. 담당자 확인: 의미를 아는 사람에게 짧게 확인받아 채웁니다. 모르는 항목은 "확인 필요"로 표시해 두는 것이 짐작으로 채우는 것보다 낫습니다.
  5. 찾기 쉬운 곳에 공개: 데이터를 쓰는 사람이 바로 찾을 수 있는 곳에 두고, 조회 화면이나 추출 파일에서 사전으로 연결되는 링크를 달아 둡니다.
사전은 "만드는 것"보다 "질문이 사전으로 가게 하는 것"이 중요합니다

"이 컬럼 무슨 뜻이에요?"라는 질문이 메신저로 오면 답을 사전에 먼저 적고 링크로 답하는 습관을 들이면, 같은 질문이 두 번 나오지 않고 사전은 자연스럽게 채워집니다.

사전을 낡지 않게: 자동으로 점검할 것들

데이터 사전이 실패하는 가장 흔한 이유는 처음 만든 뒤 아무도 갱신하지 않는 것입니다. 시스템은 계속 바뀌므로, 사람이 기억해서 고치는 대신 차이를 자동으로 찾아 알리는 구조가 필요합니다.

  • 구조 변경 감지: 매일 또는 매주 데이터베이스의 테이블·컬럼 목록을 사전과 비교해, 새로 생기거나 사라지거나 형식이 바뀐 컬럼을 담당자에게 알립니다.
  • 새 코드값 감지: 코드 컬럼에 사전에 없는 값이 처음 나타나면 알림을 보냅니다. 시스템에 새 상태가 추가됐는데 보고서는 모르는 상황을 초기에 잡을 수 있습니다.
  • 빈 값·분포 변화 감지: 평소 거의 채워지던 컬럼의 빈 값 비율이 갑자기 늘거나, 특정 코드값 비중이 크게 바뀌면 입력 방식이 바뀐 신호일 수 있으니 확인 목록에 올립니다.
  • 미작성 항목 목록: 설명이 비어 있거나 "확인 필요"로 남은 컬럼 중 자주 쓰이는 것을 주간으로 모아 담당자에게 보냅니다.

점검 결과는 사전을 자동으로 고치는 데 쓰지 않습니다. 무엇이 달라졌는지 알려 주고, 의미를 정하는 일은 사람이 하는 것이 원칙입니다.

AI는 어디에 쓰면 좋을까

AI는 사전을 빨리 채우고 찾기 쉽게 만드는 데 도움이 되지만, 회사 고유의 의미를 데이터만 보고 정확히 알 수는 없습니다.

AI에게 맡기기 좋은 일사람이 확인하거나 정할 일
컬럼명·샘플 값·관련 쿼리를 보고 설명 초안 만들기코드값과 컬럼의 실제 의미 확정
이름이 비슷하거나 값 분포가 비슷한 컬럼을 묶어 중복 후보로 제시어느 컬럼을 표준으로 쓸지 결정
"출고 완료 주문은 어디서 봐요?" 같은 질문에 사전 내용을 찾아 답하기사전에 없는 내용에 대한 답변 여부와 범위
구조 변경·새 코드값 알림을 읽기 쉬운 문장으로 요약변경이 보고서·자동화에 미치는 영향 판단

AI가 만든 설명에는 "초안" 표시를 두고 담당자가 확인한 뒤에 확정하게 하면, 빠르게 채우면서도 틀린 정의가 퍼지는 것을 막을 수 있습니다. 개인정보가 들어 있는 컬럼은 샘플 값을 AI에 넘기지 않거나 가린 상태로 다루는 것이 안전합니다.

FAQ

엑셀이나 스프레드시트로 데이터 사전을 만들어도 되나요?

처음에는 충분합니다. 중요한 것은 도구보다 한 곳에 모여 있고, 담당자가 정해져 있고, 변경될 때 갱신되는 구조입니다. 테이블이 많아지고 자동 점검을 붙이고 싶어지면 그때 데이터베이스의 컬럼 설명(comment) 기능이나 데이터 카탈로그 도구로 옮기는 것을 검토하면 됩니다.

AI에게 테이블을 보여 주면 데이터 사전을 자동으로 만들어 주지 않나요?

컬럼 이름과 샘플 값을 보고 설명 초안을 만드는 데는 도움이 됩니다. 하지만 코드값 3이 "보류"인지 "취소"인지, 금액이 부가세 포함인지 같은 회사 고유의 의미는 데이터만 보고 알 수 없어 그럴듯하지만 틀린 설명이 나올 수 있습니다. AI 초안은 담당자가 확인한 뒤에 사전에 올리는 것이 안전합니다.

지표 정의서를 이미 만들었는데 데이터 사전도 따로 필요한가요?

지표 정의서는 "매출을 어떻게 계산하는가"를, 데이터 사전은 그 계산에 쓰는 컬럼과 코드값이 "무엇을 뜻하는가"를 다룹니다. 지표 정의가 아무리 명확해도 그 안에 쓰인 상태 코드의 의미가 틀리면 숫자가 틀어지므로, 지표에 쓰이는 컬럼부터 사전을 연결해 두면 둘이 서로를 보완합니다.
