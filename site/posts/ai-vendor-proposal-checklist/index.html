AI 외주 업체, 제안서에서 무엇을 봐야 할까?

AI 자동화나 에이전트 구축 제안서를 여러 곳에서 받으면 모델 이름, 기능 목록, 개발 기간과 총액부터 비교하기 쉽습니다. 하지만 실제 운영까지 생각한다면 더 먼저 봐야 할 것은 우리 업무를 어디까지 이해했고, 데이터와 시스템을 어떻게 연결하며, 실패했을 때 어떻게 처리하는지입니다.

제안서를 기능 목록으로만 비교하면 놓치는 것

예를 들어 두 업체가 모두 “AI가 고객 문의를 자동 처리합니다”라고 제안했다고 해보겠습니다. 한쪽은 FAQ 문서를 검색해 답변만 만들고, 다른 쪽은 주문 DB와 CRM을 조회해 고객별 상태를 확인하고 위험한 요청은 담당자에게 넘깁니다. 문장으로는 비슷하지만 구축 범위와 실제 업무 효과는 크게 다릅니다.

1. 먼저 ‘무엇을 자동화하는지’ 한 문장으로 확인하세요

“AI 플랫폼 구축”, “업무 혁신”, “AI 에이전트 도입”은 프로젝트 이름이지 완료 조건이 아닙니다. 제안서에는 입력이 무엇이고 어떤 판단을 거쳐 어떤 결과를 어디에 남기는지가 보여야 합니다.

예를 들어 “매일 오전 ERP의 전일 주문 데이터를 가져와 취소율과 매출 변화를 계산하고, 이상 항목의 설명 초안을 만들어 운영팀 메신저에 전달한다” 정도라면 실제 개발 범위를 논의할 수 있습니다.

2. 데이터 연결 방법이 구체적인지 보세요

기업 AI 프로젝트는 회사 데이터를 만나면서 난이도가 달라집니다. 제안서에 “ERP 연동”이라고만 쓰여 있다면 어떤 API를 사용하는지, 필요한 필드가 실제 제공되는지, 엑셀이나 수작업 데이터는 어떻게 정리할지 확인해야 합니다.

발주 전에 물어볼 질문:
“AI는 어떤 시스템의 어떤 데이터를 어떤 방식으로 읽습니까? API가 없거나 데이터 형식이 바뀌면 어떻게 대응합니까?”

3. AI가 ‘읽는 것’과 ‘실행하는 것’을 구분하세요

매출을 조회해 설명하는 기능과 ERP 주문 상태를 변경하는 기능은 같은 난이도가 아닙니다. 실제 데이터를 수정하거나 고객에게 메시지를 발송한다면 권한 관리, 중복 실행 방지, 입력 검증과 승인 절차가 필요합니다.

제안서에서 자동 실행 범위와 사람 승인이 필요한 범위를 구분하지 않았다면 운영 단계에서 요구사항이 크게 늘어날 수 있습니다.

4. 정상 동작보다 실패했을 때를 확인하세요

데모에서는 대부분 정상 입력을 사용합니다. 운영에서는 API가 느려지고, 데이터가 비어 있고, AI가 판단하기 어려운 요청이 들어옵니다. 이때 재시도할지, 작업을 중단할지, 사람에게 넘길지 정해져 있어야 합니다.

특히 고객·결제·계약처럼 실수 비용이 큰 업무라면 “정답률을 높이겠다”보다 불확실할 때 실행하지 않는 구조가 더 중요할 수 있습니다.

5. 총액 안에 무엇이 포함됐는지 같은 기준으로 맞추세요

업체 A의 개발비가 낮아 보여도 모델/API 사용료, 클라우드, 데이터 수집 서비스, 운영 모니터링, 유지보수가 별도라면 전체 비용은 달라집니다. 반대로 초기 구축비가 높더라도 운영 도구와 인수인계까지 포함될 수 있습니다.

비교표에는 최소한 초기 구축, 외부 API·모델, 인프라, 월 운영, 유지보수, 추가 기능 변경의 비용 기준을 분리해 적는 것이 좋습니다.

6. 소스·계정·문서가 누구에게 남는지 확인하세요

프로젝트가 끝난 뒤 내부 개발자가 이어받거나 다른 업체와 협업해야 할 수도 있습니다. 저장소 접근, 클라우드 계정 소유, 환경 설정, API 목록, 데이터 구조, 운영 매뉴얼과 배포 방법이 누구에게 귀속되는지 계약 전에 확인하는 편이 안전합니다.

7. PoC의 성공 기준이 숫자 또는 판정 기준으로 정의돼 있는지 보세요

“AI 적용 가능성 확인”만으로 끝내면 PoC 이후 운영 전환 여부를 판단하기 어렵습니다. 처리 시간, 사람이 수정해야 하는 비율, 자동 처리 가능한 업무 범위, 오류 유형처럼 현재 업무와 비교할 수 있는 기준을 잡아야 합니다.

제안서 검토용 7문항

  1. 자동화할 업무의 시작과 끝이 명확한가?
  2. 연결할 데이터와 시스템, 접근 방법이 적혀 있는가?
  3. AI의 조회·판단·실행 권한이 구분돼 있는가?
  4. 오류·불확실성·외부 API 장애 때 처리 방법이 있는가?
  5. 초기비·사용료·인프라·운영·유지보수 비용을 구분할 수 있는가?
  6. 소스 코드, 계정, 기술 문서와 운영 방법을 인수받을 수 있는가?
  7. PoC 성공과 운영 전환을 판단할 기준이 있는가?

FDE가 제안 단계에서 필요한 이유

기업의 현업 담당자는 업무를 잘 알고 외주 개발사는 기술을 잘 알지만, 그 사이에서 요구사항이 번역되지 않으면 “기능은 만들었는데 업무에는 못 쓰는” 결과가 생길 수 있습니다. FDE(Forward Deployed Engineer) 성격의 역할은 현업 흐름을 직접 보고 데이터, API, 권한, 예외와 성공 기준을 기술 요구사항으로 바꾸는 데 있습니다.

그래서 AI 프로젝트에서는 업체를 고르는 것만큼 발주 전에 문제를 정확히 정의하는 과정이 중요합니다. 잘 정의된 범위는 견적 비교도 쉽게 만들고 구축 후의 변경 비용도 줄이는 데 도움이 됩니다.

FAQ

AI 외주 업체는 어떤 모델을 쓰는지가 가장 중요한가요?

모델도 중요하지만 실제 기업 프로젝트에서는 데이터 연결, 업무 범위, 권한, 예외처리, 운영과 인수인계가 성패에 더 직접적인 영향을 줄 수 있습니다.

제안 금액이 싼 업체를 선택하면 안 되나요?

금액 자체보다 포함 범위를 같은 기준으로 맞춰 비교해야 합니다. 특히 외부 API 사용료, 클라우드, 운영과 유지보수가 별도인지 확인해야 합니다.

PoC 제안서에도 운영 조건을 확인해야 하나요?

운영 전환 가능성을 보려면 PoC 단계에서도 데이터 접근, 보안, 로그, 실패 처리와 인수인계 조건을 미리 확인하는 것이 좋습니다.
