같은 부품인데 코드가 세 개라면?

구매팀은 BRK-0021로 발주하고, 생산팀은 브라켓(소)이라는 이름으로 불출하고, 쇼핑몰에는 B021-S로 올라가 있습니다. 모두 같은 부품입니다. 재고를 세어 보면 세 군데 숫자가 다 다르고, 월말에 품목별 매출을 뽑으면 같은 물건이 세 줄로 나뉘어 어느 것이 많이 팔리는지조차 알기 어렵습니다. 품목 마스터 데이터가 시스템마다 따로 자라난 회사에서 흔히 보이는 모습입니다. 이 글은 흩어진 품목·SKU 코드를 표준화하고, 다시 갈라지지 않게 운영하는 구조를 정리합니다.

품목 코드는 왜 갈라지나

품목 코드가 여러 개가 되는 데에는 대개 누군가의 잘못보다 구조적인 이유가 있습니다. 어느 경로로 갈라졌는지 알아야 표준화 뒤에 같은 일이 반복되지 않습니다.

갈라지는 경로현장에서 보이는 모습남는 문제
시스템별 독립 등록ERP, 생산 관리, 쇼핑몰 관리자, 엑셀 발주표가 각자 품목을 등록같은 물건이 시스템 수만큼 코드를 가짐
표기 차이로 인한 재등록검색했을 때 안 나와서 새로 등록. "M6 볼트"와 "볼트 M6", 전각·반각, 띄어쓰기한 시스템 안에서도 중복 코드
규격·포장 단위 혼재낱개·10개입·박스를 같은 코드로 쓰거나 반대로 색상별로 전혀 다른 코드 체계수량 단위가 섞여 재고가 안 맞음
거래처 코드 그대로 사용공급사 품번, 고객사 품번을 우리 코드처럼 입력거래처가 바뀌면 같은 물건이 새 품목이 됨
단종·개정 처리 미흡설계 변경 뒤 새 코드를 만들었지만 옛 코드도 계속 사용어느 코드가 현재 품목인지 아무도 모름

합치기 전에 먼저 정할 것: 무엇이 "같은 품목"인가

표준화 프로젝트가 중간에 멈추는 가장 흔한 이유는 기술이 아니라 같은 품목의 기준에 합의하지 못해서입니다. 구매팀에게는 공급사가 달라도 규격이 같으면 같은 품목이고, 품질팀에게는 공급사가 다르면 다른 품목입니다. 영업팀에게는 색상이 다르면 다른 상품이고, 생산팀에게는 같은 공정의 같은 자재입니다. 모두 맞는 말이라 정답을 고르는 문제가 아니라 층을 나누는 문제입니다.

  • 품목(Item): 기능과 규격이 같은 물건의 단위. 집계와 분석의 기본 기준이 됩니다.
  • 변형(Variant): 색상·사이즈·사양처럼 고객이 구분해 고르는 단위. 흔히 SKU라고 부르는 층입니다.
  • 단위(Unit): 낱개·팩·박스 같은 거래 단위. 기준 단위와 입수량으로 환산됩니다.
  • 공급원(Source): 어느 공급사의 어떤 품번으로 들어오는지. 품목의 속성이지 별도 품목이 아닙니다.
기준을 정할 때 한 가지 원칙

"어느 층에서 재고를 세고, 어느 층에서 매출을 보고, 어느 층에서 발주하는가"를 먼저 적어 보세요. 세 질문의 답이 각 층의 쓰임새를 정해 주고, 그 뒤에야 어떤 코드를 합치고 어떤 코드를 남길지 결정할 수 있습니다.

품목 마스터의 표준 항목

층이 정해지면 품목 마스터에 반드시 들어갈 항목과 각 항목의 규칙을 문서로 만듭니다. 항목이 많을 필요는 없습니다. 중요한 것은 누가 등록해도 같은 값이 나오는 규칙입니다.

항목규칙흔한 실수
대표 코드의미를 담지 않는 고정 길이 코드, 한 번 부여하면 재사용 금지분류·규격을 코드에 넣어 두어 분류가 바뀌면 코드도 바뀜
표준 품명"품목군 + 규격 + 재질" 같은 조립 순서를 정하고 표기 규칙(단위 기호, 띄어쓰기) 고정등록자마다 순서와 약어가 다름
규격·속성품목군별로 속성 항목을 정하고 값은 선택지에서 고르게자유 입력 칸에 규격을 문장으로 적음
기준 단위재고를 세는 단위 하나를 지정(EA, kg, m 등)같은 품목을 어떤 창고는 EA, 어떤 창고는 BOX로 관리
포장 단위·입수량포장 단위마다 기준 단위 환산 수량을 함께 등록"박스"만 적고 몇 개 들었는지 없음
바코드(GTIN)유통 바코드가 있으면 그대로 등록, 내부 바코드와 구분내부에서 임의로 만든 번호를 유통 바코드 칸에 입력
상태사용 중·단종 예정·단종·대체 품목 코드단종 품목이 검색에 계속 나와 발주됨
담당자·등록일·변경 이력누가 언제 무엇을 바꿨는지 자동 기록품명이 바뀌었는데 이유를 아무도 모름

유통용 바코드는 GS1 표준에 따라 발급되는 GTIN을 쓰는 것이 일반적이고, 이 번호는 외부 거래처와 품목을 식별하는 데 유용합니다. 다만 모든 품목에 유통 바코드가 있는 것은 아니므로 내부 대표 코드와 바코드는 별도 항목으로 두어야 합니다.

기존 코드를 지우지 않고 묶는 매핑 테이블

표준 항목이 정해졌다고 기존 시스템의 코드를 일괄 변경하면 안 됩니다. 과거 전표, 거래처가 쓰는 발주 양식, 창고에 붙어 있는 라벨까지 전부 옛 코드로 되어 있기 때문입니다. 대신 원본은 그대로 두고 매핑 테이블로 연결합니다. 주소 표준화에서 원본 주소를 보존하고 표준 주소를 옆에 두는 것과 같은 원리입니다.

열내용왜 필요한가
출처 시스템ERP, 생산 관리, 쇼핑몰, 거래처명 등같은 문자열이 시스템마다 다른 물건일 수 있음
원본 코드·원본 품명그 시스템에 등록된 값 그대로되돌리기와 추적의 근거
대표 코드표준 마스터의 코드집계·분석의 기준
매칭 방법·신뢰도바코드 일치, 규격 일치, 사람 확정 등자동 매칭과 사람이 확인한 매칭을 구분
확인자·확인일매핑을 확정한 사람과 시점이의가 있을 때 누구에게 물을지 분명
유효 기간시작일·종료일설계 변경으로 매핑이 바뀌는 경우 이력 보존

매핑 테이블이 있으면 각 시스템은 지금처럼 자기 코드를 쓰고, 데이터가 모이는 지점에서만 대표 코드로 변환됩니다. 재고 통합 조회, 품목별 매출 집계, 발주 추천 같은 일이 모두 이 변환 뒤에 이루어집니다. 시간이 지나 시스템을 교체할 때도 이 테이블이 이전 작업의 기준이 됩니다.

AI가 맡을 일과 사람이 확정할 일

품목이 수천 개를 넘으면 매핑 후보를 사람이 전부 찾기 어렵습니다. "브라켓 소 SUS 2T"와 "BRACKET(S) STS 2.0t"가 같은 품목이라는 판단은 규칙으로 쓰기 어렵고, 이런 유사 표기 매칭이 AI가 잘하는 일입니다. 다만 AI는 후보를 내고 사람이 확정하는 구조여야 합니다.

AI에게 맡길 일사람이 맡을 일
품명·규격 문자열을 표준 속성(품목군, 치수, 재질, 단위)으로 분해해 제안품목군별 속성 체계 정의, 분해 결과 샘플 검토
속성이 같은 품목끼리 묶어 매핑 후보와 근거 제시후보 확정, 특히 신뢰도 낮은 건 직접 판단
단위·입수량 표기("10EA/BOX", "박스(10)")를 구조화기준 단위 결정, 환산 수량 검증
표준 품명 규칙에 맞춰 품명 초안 생성최종 품명 승인
신규 등록 요청이 기존 품목과 겹치는지 사전 경고겹침 여부 최종 결정
자동 확정을 허용할 범위를 미리 정하세요

바코드가 일치하거나 규격 속성이 모두 같은 경우처럼 근거가 분명한 매칭만 자동 확정하고, 품명 유사도만으로 묶인 후보는 반드시 사람이 확인하게 합니다. 안전 부품, 의약·식품처럼 잘못 합치면 현장 사고로 이어지는 품목군은 자동 확정 대상에서 아예 제외하는 편이 낫습니다.

한 번 정리로 끝내지 않는 운영 흐름

품목 마스터는 한 번 정리해도 몇 달 지나면 다시 흐트러집니다. 새 품목은 계속 들어오고, 급한 발주 때문에 임시 코드가 생기기 때문입니다. 정리 작업보다 중요한 것이 갈라지지 않게 막는 운영 흐름입니다.

  1. 신규 등록 게이트: 어느 시스템에서든 품목을 새로 만들 때 표준 마스터에 먼저 등록 요청이 들어오게 합니다. 요청 시점에 기존 품목과의 유사 후보를 보여 주고, 담당자가 "새 품목"임을 확인해야 코드가 발급됩니다.
  2. 단일 발급 주체: 대표 코드는 한 곳에서만 발급하고, 다른 시스템은 그 코드를 받아 등록합니다. 각 시스템의 자체 코드가 꼭 필요하면 발급과 동시에 매핑 테이블에 기록합니다.
  3. 주기 점검: 주 1회 정도 전체 시스템의 품목 목록을 받아 매핑되지 않은 코드, 표준 품명 규칙 위반, 단종 품목의 신규 거래를 찾아 담당자에게 목록으로 보냅니다.
  4. 변경 전파: 품명이나 상태가 바뀌면 매핑된 모든 시스템에 자동으로 반영하거나, 최소한 반영해야 할 목록을 만들어 줍니다.
  5. 지표 관리: 매핑되지 않은 코드 수, 신규 등록 중 중복으로 판정된 비율, 자동 매칭을 사람이 뒤집은 비율을 매달 봅니다. 이 숫자가 내려가지 않으면 규칙이나 게이트에 구멍이 있다는 뜻입니다.

도입 전 체크리스트

  1. 품목이 등록돼 있는 시스템과 엑셀 파일을 전부 나열하고 각각의 품목 수를 세어 보기
  2. 가장 많이 거래되는 품목 50개를 골라 시스템별로 코드가 몇 개씩인지 직접 확인하기
  3. 구매·생산·영업·품질 담당자와 "같은 품목"의 층(품목·변형·단위·공급원)에 합의하기
  4. 품목군별 표준 속성과 표준 품명 규칙 초안을 만들고 실제 품목 20개에 적용해 보기
  5. 대표 코드 발급 주체와 신규 등록 절차를 정하고 임시 코드가 생기는 경로를 막기
  6. 기존 코드는 변경하지 않고 매핑 테이블로 연결한다는 원칙을 관련 팀에 공유하기
  7. 자동 확정 허용 범위와 사람이 반드시 확인할 품목군을 문서로 남기기
  8. 매핑되지 않은 코드 수를 첫 지표로 정하고 매달 추적하기

FAQ

ERP 품목 코드를 전부 새 체계로 바꾸면 해결되나요?

권하지 않습니다. 기존 코드는 과거 전표, 거래처 발주서, 바코드 라벨, 엑셀 양식에 이미 깊게 박혀 있어서 한 번에 바꾸면 그 모든 곳에서 오류가 납니다. 대표 코드를 따로 정하고 기존 코드들을 매핑 테이블로 대표 코드에 연결하는 방식이 안전합니다. 각 시스템은 원래 코드를 그대로 쓰고, 집계와 분석만 대표 코드 기준으로 하면 됩니다.

낱개와 박스처럼 포장 단위가 다른 것도 같은 품목으로 묶어야 하나요?

같은 품목의 다른 판매 단위로 다뤄야 합니다. 기준 단위(예: 낱개)를 정하고 박스·팩 같은 포장 단위는 기준 단위로 환산되는 입수량과 함께 별도 코드로 등록하는 방식이 일반적입니다. 이렇게 해야 재고는 기준 단위로 합산하고, 판매는 포장 단위별로 볼 수 있습니다. 환산 정보 없이 하나로 합치면 수량이 틀어집니다.

거래처가 쓰는 품목 코드와 우리 코드가 다른데 어떻게 하나요?

거래처별 코드도 매핑 테이블에 한 축으로 넣습니다. 거래처 코드, 거래처 품명, 우리 대표 코드, 확인 일자, 확인자를 함께 저장해 두면 발주서나 견적서를 받을 때 자동으로 우리 코드로 변환할 수 있습니다. 거래처가 코드를 바꾸는 일도 있으니 매칭이 실패한 건은 자동 확정하지 말고 담당자에게 넘겨 매핑을 추가하게 하는 것이 좋습니다.
