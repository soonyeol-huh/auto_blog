ERP 바꾸면서 옛 데이터는 엑셀로 옮겨 붙이면 되나요?

새 ERP로 바꾼 첫 달, 회계팀이 작년 매출을 뽑아 보니 옛 시스템 숫자와 맞지 않습니다. 영업팀은 거래처 절반의 담당자 칸이 비어 있다고 하고, 창고에서는 단종시킨 품목이 재고 목록에 다시 살아났다고 합니다. 이관을 맡은 쪽은 "건수는 전부 맞다"고 답합니다. 시스템 교체 프로젝트에서 가장 늦게, 가장 아프게 드러나는 문제가 데이터 이관입니다. 이 글은 옛 시스템의 데이터를 새 시스템으로 옮길 때 무엇을 먼저 정하고, 어떻게 검증하고, 전환 당일을 어떻게 넘기는지 정리합니다.

건수가 맞아도 데이터가 틀리는 이유

이관 보고서의 "원본 12,480건, 이관 12,480건" 같은 줄은 안심을 주지만, 건수는 가장 쉬운 검사일 뿐입니다. 실제 사고는 건수가 맞는 상태에서 값의 의미, 코드, 형식, 관계가 어긋나며 생깁니다. 어떤 유형이 있는지 알아야 검증 항목을 빠짐없이 세울 수 있습니다.

문제 유형현장에서 보이는 모습원인
항목 의미 변화옛 시스템의 "거래일"이 새 시스템의 "전표일"로 들어가 월별 매출이 달라짐이름이 비슷한 항목을 뜻 확인 없이 대응
코드 체계 불일치옛 고객 등급 A·B·C가 새 시스템 등급 1~5 중 하나로 뭉뚱그려짐선택지 값 변환표 없이 이관
잘린 값·형식 변환긴 주소가 중간에서 잘림, 날짜의 월·일이 바뀜, 앞자리 0이 사라진 번호자릿수·형식 제한을 확인하지 않음
관계 끊김거래처는 옮겨졌는데 담당자·배송지·계약이 연결되지 않음새 시스템이 ID를 새로 발급하면서 참조가 깨짐
상태 되살아남단종 품목, 거래 중지 거래처가 "사용 중"으로 나타남상태 항목을 안 옮기거나 기본값으로 채움
이력·첨부 소실변경 이력, 메모, 첨부 파일이 새 시스템에 없음이관 범위에 처음부터 들어 있지 않음
중복 유입같은 거래처가 두 번, 또는 리허설 데이터가 남아 거래가 두 배정리 없이 이관, 리허설 잔재 미삭제

옮기기 전에 정할 것: 범위·기간·정리 수준

이관은 "전부 옮긴다"로 시작하면 끝나지 않습니다. 데이터 종류마다 어디까지, 언제까지, 어떤 상태로 옮길지 먼저 정해야 매핑과 검증의 양이 정해집니다.

  • 마스터 데이터(거래처·품목·계정·사원·창고): 현재 사용 중인 것은 전부. 사용 중지된 것은 미결 거래가 걸려 있는 것만.
  • 미결 거래(미수금·미지급금, 미출고 주문, 진행 중 계약, 열린 클레임): 전부. 새 시스템에서 이어서 처리해야 하는 것들입니다.
  • 완료된 거래 이력: 업무상 조회가 필요한 기간을 정해 그 범위만. 예를 들어 영업은 최근 몇 년의 거래 이력, 품질은 출하 추적에 필요한 기간처럼 팀별로 요구가 다릅니다.
  • 집계·통계: 옮기지 않고 새 시스템에서 다시 계산하는 것이 원칙. 옛 집계와 새 집계가 다르면 그 자체가 검증 신호가 됩니다.
  • 정리 수준: 마스터는 이관 전에 중복과 표기를 정리하고, 거래 이력은 원본 그대로 옮깁니다. 이력까지 손대면 과거 숫자가 바뀌어 비교가 불가능해집니다.
옮기지 않는 데이터도 결정입니다

이관 범위 밖의 데이터를 어떻게 할지 문서로 남기세요. 옛 시스템을 일정 기간 읽기 전용으로 유지할지, 파일로 내보내 보관할지, 누가 접근할 수 있는지가 포함되어야 합니다. 회계·세무 자료처럼 법령상 보존 의무가 있는 자료는 보관 형태와 기간을 회계·세무 전문가와 확인한 뒤 정합니다.

매핑 정의서: 옛 항목과 새 항목을 한 장에

이관의 설계도는 매핑 정의서입니다. 옛 시스템의 항목 하나하나가 새 시스템의 어느 항목으로, 어떤 규칙으로 가는지 적은 표입니다. 이 표가 없으면 이관 담당자가 항목 이름만 보고 짝을 맞추게 되고, 위의 "항목 의미 변화"가 여기서 생깁니다.

열내용예
원본 테이블·항목옛 시스템에서의 위치와 항목명, 데이터 형식거래처 마스터 > CUST_GRADE (문자 1자)
대상 테이블·항목새 시스템에서의 위치와 항목명, 데이터 형식고객 > 고객 등급 (선택지)
변환 규칙그대로 / 코드 변환표 / 계산 / 분리·결합코드 변환표 "등급" 시트 적용
기본값·결측 처리비어 있을 때 넣을 값과 그 이유빈 등급은 "미분류"로 넣고 예외 목록에 기록
형식·길이 제한자릿수, 날짜 형식, 허용 문자, 초과 시 처리주소 50자 초과분은 상세 주소 항목으로 분리
키 대응옛 ID와 새 ID의 대응표 보관 여부옛 거래처 번호를 새 고객의 "구 코드" 항목에 저장
업무 담당자·확정일이 매핑을 확인한 업무 담당자와 날짜영업관리팀 확인

매핑 정의서는 IT가 아니라 그 데이터를 쓰는 업무 담당자가 승인해야 합니다. 거래일과 전표일의 차이를 아는 사람은 회계팀이고, 고객 등급 A가 새 체계의 어디에 해당하는지 아는 사람은 영업팀입니다. 코드 변환표는 별도 시트로 만들어 선택지 값마다 대응을 적고, 옛 ID와 새 ID 대응표는 이관이 끝난 뒤에도 보관합니다. 몇 달 뒤 "옛 시스템에서 이 거래처 번호였는데요"라는 문의가 반드시 오기 때문입니다.

검증은 네 겹으로: 건수·합계·샘플·업무 시나리오

검증을 건수 비교 한 가지로 끝내면 위 표의 문제 대부분을 놓칩니다. 아래 네 겹을 모두 거쳐야 하고, 각 겹은 서로 다른 유형의 문제를 잡습니다.

겹무엇을어떻게잡히는 문제
건수테이블별 건수원본과 대상을 상태별·연도별·거래처 유형별로 쪼개서 비교누락, 중복, 필터 조건 오류
합계·분포금액·수량 합계와 항목별 값 분포거래처별 채권 잔액 합계, 등급별 고객 수, 비어 있는 항목 비율변환 오류, 잘린 값, 기본값 과다
샘플 대조개별 건을 화면에서 나란히 비교무작위 표본에 더해 가장 오래된 건, 금액이 가장 큰 건, 특수문자가 든 건, 취소·반품 건을 일부러 포함형식, 관계 끊김, 이력·첨부 소실
업무 시나리오실제 업무를 새 시스템에서 끝까지 수행미수금 입금 처리, 미출고 주문의 출고, 기존 견적의 재발행, 단종 품목 발주 시도사람이 써야만 드러나는 문제

앞의 두 겹은 스크립트로 자동화해서 리허설마다 같은 검사를 반복하고, 결과는 "맞음/틀림"이 아니라 예외 목록으로 뽑습니다. 어느 테이블의 어느 건이 어떤 검사에서 걸렸는지가 남아야 매핑을 고칠 수 있습니다.

맞춰야 할 숫자를 먼저 정하세요

검증을 시작하기 전에 "옛 시스템과 새 시스템에서 반드시 같아야 하는 보고서 숫자"의 명단을 만듭니다. 월별 매출 합계, 거래처별 채권·채무 잔액, 품목별 재고 수량, 미결 주문 건수처럼 각 팀이 매달 보는 숫자들입니다. 이 명단이 검증의 합격 기준이 되고, 전환 뒤 첫 마감에서 다시 쓰입니다.

리허설과 전환 당일

이관을 한 번에 성공시키는 방법은 없습니다. 전체 데이터로 끝까지 해 보는 리허설을 반복하고, 전환 당일은 리허설에서 검증된 절차를 그대로 다시 실행하는 날이어야 합니다.

  1. 리허설 1차: 전체 데이터로 처음부터 끝까지 이관하고 네 겹 검증을 돌립니다. 걸린 시간과 예외 목록을 기록합니다.
  2. 매핑 수정과 리허설 2차: 예외 목록을 보고 매핑 정의서와 변환표를 고친 뒤 다시 전체 이관합니다. 리허설은 최소 두 번, 마지막 리허설은 전환 당일과 같은 순서·같은 담당자로 진행합니다.
  3. 입력 동결 공지: 옛 시스템 입력을 멈추는 시점과 재개 시점, 그 사이에 생긴 거래를 어떻게 적어 두었다가 새 시스템에 넣을지(수기 목록 양식)를 전 부서에 미리 알립니다.
  4. 최종 이관과 자동 검증: 리허설 데이터를 모두 지운 상태에서 최종 이관을 실행하고 자동 검증을 돌립니다. 예외 목록이 비어 있거나, 남은 예외마다 담당자의 승인 기록이 있어야 다음으로 갑니다.
  5. 업무 담당자 승인: 각 팀이 맞춰야 할 숫자 명단과 업무 시나리오를 직접 확인하고 체크리스트에 서명합니다.
  6. 옛 시스템 읽기 전용 유지: 전환 뒤 옛 시스템은 입력을 막고 조회만 열어 둡니다. 끄는 시점은 별도로 정합니다.
  7. 첫 마감 비교: 전환 뒤 첫 월 마감에서 맞춰야 할 숫자 명단을 옛 시스템 기준과 한 번 더 비교해 보고서로 남깁니다.

AI가 맡을 일과 사람이 확정할 일

항목이 수백 개, 코드 값이 수천 개인 이관에서 매핑 후보를 사람이 처음부터 다 찾기는 어렵습니다. 옛 시스템의 항목 설명과 새 시스템의 항목 설명을 읽고 짝을 제안하는 일, 자유 입력 값을 구조로 나누는 일은 AI가 잘합니다. 다만 값을 실제로 바꾸는 작업은 AI가 아니라 규칙 기반 스크립트가 해야 결과를 재현하고 검증할 수 있습니다.

AI에게 맡길 일사람이 맡을 일
옛·새 시스템의 항목명·설명·샘플 값을 읽고 매핑 후보와 근거 제안매핑 확정, 특히 이름은 비슷하지만 뜻이 다른 항목 판별
비고·주소·품명 같은 자유 입력 값을 구조화된 항목으로 분해하는 규칙 초안분해 규칙 검토, 표본으로 결과 확인
옛 등급·분류 값과 새 선택지의 코드 변환표 초안변환 기준 결정, 애매한 값의 처리 방침
검증 예외 목록을 유형별로 묶고 어떤 매핑이 원인인지 요약수정 방법 결정, 예외 승인
중복 가능성이 있는 거래처·품목 후보 제시합칠지 여부 결정
값 변환은 AI에게 맡기지 않습니다

금액·수량·날짜·코드처럼 정확히 옮겨야 하는 값은 매핑 정의서에 적힌 규칙대로 스크립트가 변환하고, 같은 입력에 항상 같은 출력이 나와야 합니다. AI는 그 규칙을 만드는 과정을 돕는 역할에 두고, AI가 만든 초안도 사람이 확정한 뒤에만 스크립트에 들어가게 합니다.

도입 전 체크리스트

  1. 옛 시스템의 테이블·항목 목록과 건수를 뽑아 마스터·미결 거래·완료 이력·집계로 분류하기
  2. 데이터 종류별로 이관 범위와 기간을 정하고, 옮기지 않는 데이터의 보관 방식까지 문서로 남기기
  3. 법령상 보존 의무가 있는 자료의 보관 형태와 기간을 회계·세무 전문가와 확인하기
  4. 매핑 정의서와 코드 변환표를 만들고 각 항목을 업무 담당자가 승인하기
  5. 옛 ID와 새 ID 대응표를 어디에 어떻게 보관할지 정하기
  6. 팀별로 맞춰야 할 보고서 숫자 명단을 만들고 건수·합계 검증 스크립트를 준비하기
  7. 전체 데이터 리허설을 최소 두 번 일정에 넣고 입력 동결 기간을 전 부서에 공지하기
  8. 전환 뒤 첫 월 마감에서 옛·새 숫자 비교 보고를 누가 할지 정하기

FAQ

옛 시스템 데이터를 전부 새 시스템으로 옮겨야 하나요?

아니요. 거래처·품목 같은 마스터와 미수금·미출고 주문 같은 미결 거래는 전부 옮기고, 완료된 거래 이력은 업무상 조회가 필요한 기간만 옮기는 방식이 일반적입니다. 나머지는 옛 시스템을 읽기 전용으로 두거나 파일로 내보내 보관합니다. 오래된 이력까지 다 옮기면 매핑과 검증 비용이 그만큼 커지고 새 시스템에도 부담이 됩니다. 다만 회계·세무 자료처럼 보존 의무가 있는 자료는 어떤 형태로 얼마나 보관할지 회계·세무 전문가와 확인한 뒤 결정해야 합니다.

이관하면서 중복 거래처 정리 같은 데이터 정리도 함께 하면 되나요?

마스터 데이터는 이관 전에 정리하는 편이 낫습니다. 중복 거래처를 그대로 옮기면 새 시스템에서 다시 합쳐야 하고, 그 사이 거래 이력이 양쪽에 나뉘어 붙습니다. 다만 정리와 이관을 한 프로젝트로 묶으면 일정이 늘어지기 쉬우니 정리 범위를 거래 중인 거래처·품목으로 제한하고, 완료된 거래 이력은 원본 그대로 옮기는 것이 현실적입니다. 정리 결과는 옛 코드와 새 코드의 대응표로 남겨 두어야 나중에 추적할 수 있습니다.

옛 시스템은 언제 꺼도 되나요?

전환 직후에 끄는 것은 권하지 않습니다. 최소한 첫 월 마감을 새 시스템에서 치르고 옛 시스템 숫자와 비교한 뒤, 옛 시스템 조회 요청이 더 이상 들어오지 않을 때 끄는 시점을 정하는 것이 안전합니다. 끄기 전에는 옛 데이터를 파일로 내보내 옛 ID와 새 ID 대응표, 매핑 정의서와 함께 보관해 두어야 나중에 문의가 와도 추적할 수 있습니다.
