대시보드가 있어도 아무도 안 본다면? 데이터를 행동으로 바꾸는 자동화 설계

데이터를 잘 모아 대시보드까지 만들었는데도 담당자가 매일 직접 열어보고, 숫자를 판단하고, 메신저로 전달하고, 다시 ERP나 광고 관리자에서 조치한다면 업무는 아직 절반만 자동화된 상태입니다. 다음 단계는 숫자를 보여주는 시스템에서 행동을 시작하는 시스템으로 바꾸는 것입니다.

대시보드가 실패하는 가장 흔한 이유는 ‘다음 행동’이 없기 때문입니다

대시보드는 데이터를 한눈에 보는 데 강합니다. 하지만 담당자가 바쁜 날에는 아예 열어보지 않을 수 있고, 숫자를 봤더라도 무엇을 해야 하는지 다시 판단해야 합니다. 결국 데이터 확인과 실제 조치 사이에 사람이 수동으로 연결하는 단계가 남습니다.

단계대시보드 중심행동 중심 자동화
데이터 확인사람이 화면을 열어봄시스템이 조건·이상치를 감지
판단 전달메신저·메일로 수동 공유담당자에게 필요한 맥락과 함께 알림
조치ERP·CRM·광고 도구에 다시 접속승인 후 API 또는 워크플로 실행
결과 추적사람이 다시 확인실행 로그와 결과를 자동 기록

핵심은 ‘지표’가 아니라 ‘결정 규칙’입니다

예를 들어 재고 대시보드에 상품별 재고 수량이 보인다고 해보겠습니다. 운영자가 필요한 것은 숫자 137개를 보는 일이 아니라 “어떤 상품에 지금 조치해야 하는가?”입니다.

지표: 재고 18개
맥락: 최근 7일 판매 속도 상승, 입고까지 5일
판단: 3일 내 품절 가능성 높음
행동: 담당 MD에게 발주 검토 요청
실행: 승인 시 ERP에 발주 초안 생성

이렇게 지표 뒤에 조건과 행동을 붙이면 대시보드가 업무 시스템으로 바뀌기 시작합니다.

구현 구조: 데이터 → 이벤트 → 판단 → 승인 → 실행

1. 신뢰할 수 있는 데이터 계층을 먼저 만듭니다

ERP, CRM, 광고 플랫폼, 쇼핑몰, 경쟁사 데이터가 서로 다른 기준으로 들어오면 잘못된 알림이 생깁니다. 상품 ID, 고객 ID, 시간 기준, 데이터 갱신 주기를 통일하고 누락·중복·지연을 검증해야 합니다.

2. 모든 숫자가 아니라 ‘변화’를 이벤트로 만듭니다

예를 들어 매출이 1,200만 원이라는 값보다 “평소 같은 요일 대비 주문 전환율이 급락했다”, “경쟁사 두 곳이 동시에 가격을 내렸다”, “재고 소진 예상일이 리드타임보다 짧아졌다” 같은 변화가 업무 이벤트가 됩니다.

3. 담당자에게 맥락까지 함께 전달합니다

“전환율 하락”만 보내면 담당자는 다시 대시보드를 열어 원인을 찾아야 합니다. 최근 추이, 관련 캠페인, 재고 상태, 변경된 경쟁사 가격처럼 판단에 필요한 정보를 한 번에 묶어 보내야 알림이 실제 행동으로 이어집니다.

4. 위험도에 따라 자동 실행과 승인 실행을 나눕니다

데이터 새로고침, 리포트 생성, 내부 티켓 생성처럼 되돌리기 쉬운 작업은 자동 실행할 수 있습니다. 반면 가격 변경, 광고비 증액, 고객 환불, 계약·결제처럼 영향이 큰 조치는 사람이 승인하도록 설계하는 편이 안전합니다.

5. 실행 결과를 다시 데이터로 남깁니다

누가 어떤 신호를 보고 무엇을 승인했는지, API 호출이 성공했는지, 실행 뒤 매출·전환·재고가 어떻게 변했는지를 기록해야 합니다. 그래야 자동화 규칙이 실제로 도움이 됐는지 개선할 수 있습니다.

실제 예시: 광고 성과 대시보드를 ‘운영 시스템’으로 바꾸기

여러 광고 채널을 운영하는 이커머스 팀을 가정해보겠습니다. 기존에는 담당자가 매일 광고 관리자와 대시보드를 열어 ROAS, 전환율, 광고비를 보고 캠페인을 조정합니다.

행동 중심으로 바꾸면 데이터 파이프라인이 광고비, 전환, 매출, 재고를 일정 주기로 갱신합니다. 시스템은 단순 임계치뿐 아니라 최근 평균 대비 변화와 재고 상황을 함께 검사합니다. 예를 들어 광고비는 증가했지만 전환율이 급락했고 해당 상품 재고도 충분한 경우 운영 검토 이벤트를 생성합니다.

담당자는 메신저나 업무 화면에서 “최근 3일 변화, 관련 캠페인, 상품 매출, 재고”를 한 번에 보고 일시중지 또는 예산 조정안을 승인할 수 있습니다. 승인 후 광고 API가 실행되고 결과가 로그에 저장됩니다.

AI는 ‘규칙을 대신하는 모델’보다 ‘판단을 돕는 계층’으로 시작하는 편이 좋습니다

모든 결정을 LLM에게 맡길 필요는 없습니다. 금액, 재고, 전환율처럼 계산 가능한 조건은 코드나 분석 규칙으로 먼저 좁히고, AI는 관련 상황을 요약하거나 여러 신호를 설명하고 담당자가 확인할 항목을 제안하는 데 활용할 수 있습니다.

예를 들어 시스템이 “전환율 급락” 이벤트를 확정한 뒤 AI가 광고 소재 변경 이력, 고객 문의, 리뷰, 경쟁사 가격 변화 등을 함께 읽고 가능한 원인을 짧게 정리하도록 만들 수 있습니다. 최종 예산 변경은 사람이 승인합니다.

PoC는 ‘대시보드 전체’가 아니라 한 가지 행동으로 시작합니다

처음부터 회사의 모든 KPI를 자동화할 필요는 없습니다. “품절 위험 상품을 오전 9시에 알려주고 발주 초안을 만든다”, “광고 이상 캠페인을 찾고 담당자에게 조정안을 보낸다”처럼 한 가지 업무 행동을 끝까지 연결하는 편이 좋습니다.

이렇게 해야 데이터 연결, 조건 정확도, 알림 피로도, 승인 흐름, API 실행과 ROI를 실제로 검증할 수 있습니다. 성공하면 같은 구조를 다른 상품군이나 부서로 확장할 수 있습니다.

FAQ

대시보드가 있으면 자동화가 된 것 아닌가요?

대시보드는 상태를 보여주는 도구입니다. 실제 자동화는 조건을 감지하고 담당자에게 전달하며 필요하면 승인 후 시스템에서 조치가 실행되는 흐름까지 설계해야 완성됩니다.

모든 이상 신호를 자동 실행으로 연결해도 되나요?

권장하지 않습니다. 고객, 가격, 결제, 계약처럼 영향이 큰 조치는 사람 승인을 두고, 위험이 낮고 되돌리기 쉬운 작업부터 자동 실행하는 것이 안전합니다.

어떤 업무부터 시작하면 좋나요?

담당자가 매일 같은 지표를 확인하고 일정 조건이 되면 반복적으로 같은 조치를 하는 업무가 좋은 후보입니다. 조건과 행동이 명확할수록 PoC 범위를 작게 잡기 쉽습니다.
