"그거 누구한테 말하면 돼요?" 사내 IT·총무 요청, 아직 메신저로 받고 계신가요

모니터가 안 켜진다는 메시지는 IT 담당자 개인 메신저로, 회의실 에어컨 고장은 복도에서 말로, 공유 폴더 권한 요청은 메일로 들어옵니다. 담당자는 하루 종일 바쁜데 요청한 사람은 "아직도 안 됐네" 하고, 몇 건은 아예 잊힙니다. 사내 요청이 밀리는 이유는 담당자가 게을러서가 아니라 요청이 들어오는 길과 처리 기준과 진행 상태가 한곳에 모여 있지 않아서입니다.

사내 요청이 처리되지 않고 사라지는 이유

사내 요청은 대부분 급하지 않아 보이는 작은 일입니다. 그래서 정식 절차 없이 가장 편한 채널로 던져지고, 받는 사람도 "이따 해야지" 하고 넘깁니다. 문제는 이런 작은 요청이 하루에도 여러 건 쌓인다는 점입니다.

  • 입구가 여러 개: 개인 메신저, 단체방, 메일, 구두, 포스트잇까지 요청이 들어오는 곳이 제각각이라 담당자가 전체 목록을 볼 수 없습니다.
  • 정보가 빠져 있음: "프린터가 이상해요"만으로는 어느 층 어떤 기기인지, 어떤 증상인지 알 수 없어 되물어야 합니다.
  • 담당자가 불분명: IT인지 총무인지 시설 관리인지 애매한 요청은 서로 미루다 멈춥니다.
  • 상태가 안 보임: 요청자는 처리 중인지 잊힌 건지 알 수 없어 같은 요청을 다시 하거나 직접 해결하려다 일을 키웁니다.

결국 담당자의 기억과 메신저 스크롤이 업무 시스템 역할을 하고 있는 셈입니다. 담당자가 휴가를 가거나 바뀌면 진행 중이던 요청이 통째로 사라집니다.

요청 유형 목록부터 만든다

자동화의 출발점은 도구가 아니라 어떤 요청이 들어오는지 목록으로 꺼내는 일입니다. 지난 몇 주간 메신저와 메일에서 받은 요청을 모아 보면 대부분 몇 가지 유형으로 묶입니다.

각 유형마다 목표 처리 기간과 긴급도 기준을 회사 상황에 맞게 정해 둡니다. 숫자 자체보다 "업무가 완전히 멈춘 장애는 당일, 비품 보충은 정기 구매일에 맞춰" 같은 기준이 합의돼 있는지가 중요합니다. 비용이 드는 비품·장비 요청은 기존 구매 승인 흐름으로 넘기는 연결점도 여기서 정합니다.

접수 창구는 하나로, 입구는 익숙한 곳에

직원에게 새 시스템 사용법을 가르치는 것보다, 이미 쓰는 메신저나 그룹웨어를 입구로 두고 뒤에서 하나의 요청 목록으로 모으는 구조가 정착이 빠릅니다.

  1. 요청 양식: 유형을 먼저 고르면 그 유형에 필요한 항목만 나오는 짧은 양식을 메신저 메뉴나 그룹웨어 링크로 제공합니다.
  2. 메신저·메일 접수: 자유 형식으로 들어온 요청도 같은 목록에 요청 건으로 등록하고, 빠진 정보는 자동으로 되묻습니다.
  3. 요청 번호와 기록: 모든 요청에 번호, 요청자, 접수 시각, 유형, 담당자, 상태, 처리 내용을 남깁니다.
  4. 개인 메신저로 온 요청: 담당자가 받은 메시지를 한 번의 동작으로 요청 목록에 옮길 수 있게 해 두면 입구가 완전히 통일되지 않아도 누락이 줄어듭니다.
요청 양식은 짧을수록 잘 쓰입니다. 항목이 많은 양식은 결국 다시 메신저로 돌아가게 만듭니다. 유형별로 꼭 필요한 정보만 받고, 나머지는 담당자가 처리하면서 채우는 편이 낫습니다.

분류와 배정은 규칙 먼저, AI는 보조

담당자 배정은 대부분 규칙으로 충분합니다. 유형·위치·시스템 이름에 따라 담당자와 대리 담당자를 표로 정해 두면 시스템이 그대로 따릅니다.

AI는 규칙이 적용되기 전 단계, 즉 자유롭게 쓴 요청을 정리하는 일에서 쓸모가 있습니다.

  • "3층 회의실 화면이 안 나와요" 같은 문장에서 유형(IT 장애), 위치(3층 회의실), 증상을 뽑아 양식 항목에 채우는 일
  • 빠진 정보를 찾아 "어떤 회의실인가요?"처럼 되물을 질문을 만드는 일
  • 비슷한 과거 요청과 그때의 처리 방법을 찾아 담당자에게 함께 보여주는 일
  • 사내 안내 문서에 답이 있는 단순 문의라면 해당 문서를 찾아 요청자에게 먼저 안내하는 일

다만 AI의 분류에는 확신도를 함께 남기고, 확신도가 낮거나 여러 유형에 걸친 요청은 담당자가 직접 분류하도록 합니다. 계정 권한 부여, 보안 사고 의심 신고, 비용이 드는 요청은 AI가 처리를 확정하지 않도록 설계해야 합니다. 이런 요청은 정해진 승인자를 반드시 거치게 하고, 요청 내용과 승인 이력을 그대로 기록합니다.

진행 상태와 지연 알림

사내 요청 자동화에서 직원들이 가장 먼저 체감하는 변화는 "내 요청이 지금 어디 있는지 보인다"는 점입니다.

  1. 상태 표준화: 접수, 정보 보완 요청, 처리 중, 외부 업체 대기, 완료, 요청자 확인 같은 상태를 모든 요청에 붙입니다.
  2. 상태 변경 알림: 상태가 바뀔 때마다 요청자에게 같은 메신저로 알려 확인 연락을 줄입니다.
  3. 지연 기준: 유형별 목표 처리 기간을 넘기면 담당자에게 다시 알리고, 그래도 움직임이 없으면 대리 담당자나 관리자에게 알립니다.
  4. 완료 확인: 담당자가 완료 처리하면 요청자가 해결 여부를 확인하게 하고, 해결되지 않았다면 같은 요청 번호로 다시 열립니다.
  5. 부재 처리: 담당자 휴가·출장 일정을 등록해 두면 그 기간의 새 요청은 대리 담당자에게 자동으로 배정됩니다.

쌓인 요청 데이터로 반복 요청을 줄인다

요청이 한 목록에 쌓이기 시작하면 그동안 감으로만 알던 것이 숫자로 보입니다. 어떤 유형이 많은지, 어느 층·어느 기기에서 같은 장애가 반복되는지, 어떤 요청이 자주 지연되는지가 드러납니다.

  • 같은 질문이 반복되면 사내 안내 문서나 FAQ로 만들어 요청 양식 앞단에 먼저 보여줍니다.
  • 같은 기기의 장애가 반복되면 수리 대신 교체나 점검 주기 조정을 검토할 근거가 됩니다.
  • 정보 보완 요청이 자주 생기는 유형은 양식 항목을 고칩니다.
  • 입사·퇴사 때마다 반복되는 계정·장비 요청은 묶음 요청으로 만들어 한 번에 처리합니다.

이 단계에서 요청 처리 자동화는 단순한 접수 창구를 넘어 사내 운영을 개선하는 데이터가 됩니다.

도입 전 체크리스트

  1. 최근 몇 주간 메신저·메일·구두로 받은 사내 요청을 모아 유형별로 묶어 보기
  2. 유형별 필수 정보, 기본 담당자, 대리 담당자 정하기
  3. 유형별 목표 처리 기간과 긴급도 기준을 담당 부서와 합의하기
  4. 승인이 필요한 요청(계정 권한, 비용 발생, 보안 관련)과 승인자 정하기
  5. 직원이 이미 쓰는 메신저·그룹웨어 중 어느 것을 입구로 둘지 정하기
  6. 요청 기록에 들어가는 개인정보와 보관 기간을 사내 기준에 맞게 정하기

FAQ

직원이 수십 명 규모인 회사에도 사내 요청 창구가 필요한가요?

IT·총무 담당자가 한두 명이고 요청이 메신저·구두·메일로 섞여 들어온다면 오히려 효과가 큽니다. 담당자 한 사람의 기억에 모든 요청이 의존하고 있기 때문입니다. 처음에는 요청 양식 하나와 상태가 보이는 목록만 만들어도 "그 건 어떻게 됐어요?"라는 확인 연락과 빠뜨리는 건이 줄어듭니다.

AI가 요청을 자동으로 처리해도 되나요?

AI는 자유롭게 쓴 요청을 유형별로 분류하고, 빠진 정보를 되묻고, 비슷한 과거 처리 내역이나 사내 안내 문서를 찾아 보여주는 데 적합합니다. 반면 계정 권한 부여, 보안 관련 요청, 비용이 드는 요청은 사전에 정한 승인자가 확인하도록 설계해야 합니다. AI 분류가 틀릴 수 있으므로 확신도가 낮은 건은 담당자가 직접 분류하는 단계를 둡니다.

이미 그룹웨어나 메신저를 쓰고 있으면 새 시스템을 도입해야 하나요?

꼭 그렇지는 않습니다. 직원이 익숙한 메신저나 그룹웨어 양식을 입구로 그대로 두고, 들어온 요청을 하나의 요청 목록으로 모으는 연결부터 만드는 방식이 일반적입니다. 상태 알림도 같은 메신저로 보내면 직원 입장에서는 쓰는 도구가 바뀌지 않습니다.
